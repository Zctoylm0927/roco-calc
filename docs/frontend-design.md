# 前端设计：战斗伤害范围计算器

> 状态：设计稿（2026-11-21），尚未开始写代码。
>
> 目标：在浏览器里估算对局伤害。我方精灵的性格、天分在战斗前就知道；对方只知道是哪个精灵，性格和天分未知，所以所有伤害先显示为一个范围，再通过战斗中记录的真实伤害逐步缩小。

## 1. 第一版做什么

第一版只做一条主流程：

1. 选择我方精灵、性格、天分（全部已知）。
2. 选择对方精灵（只知道种类，性格和天分未知）。
3. 选择我方技能，查看伤害范围、占对方生命的比例、能否击倒。
4. 填写双方当前的增减益、天气、星陨层数。
5. 在战斗记录里填“我方某只精灵用某技能打了对方多少血”，程序自动缩小对方的属性范围，并给出可能的性格。
6. 记录“这一轮后对方还剩百分之多少生命”，进一步缩小对方的生命范围，并排除一部分性格。

第一版暂不做：

- 对方打我方技能的伤害范围（接口预留，后面补）。
- 多只对方精灵同时追踪（数据模型预留，界面先做单只）。
- 速度先后、先手、换人。
- 特性、道具、场地、其他印记。
- 可学技能过滤（先列出全部攻击技能，用搜索框找）。

## 2. 技术方案

不安装任何新软件：

- 后端：Python 自带的 HTTP 服务（`http.server`），复用现有 `roco_calc.py`。
- 前端：普通 HTML/CSS/JavaScript，无 Node、无打包工具、无外部 CDN，断网也能用。
- 运行：`python server.py`，浏览器打开 `http://127.0.0.1:8000`。
- 服务只监听本机（127.0.0.1），局域网外无法访问。

计划新增的文件：

| 文件 | 作用 |
|------|------|
| `roco_analysis.py` | 范围计算核心：候选属性、伤害范围、战斗记录过滤 |
| `analyze.py` | 临时的命令行演示，用于验证核心；网页完成后保留作调试工具 |
| `server.py` | 本地网页服务，提供 JSON 接口和静态页面 |
| `web/index.html` | 页面结构 |
| `web/app.js` | 页面交互 |
| `web/style.css` | 样式 |

## 3. 页面结构

参考 tzrain 战斗页的「左右两栏 + 技能伤害卡片」，但对方一栏显示范围而不是固定值。

```text
┌──────────────────────────────────────────────────────────┐
│ 天气 [雨天 ▾]              星陨层数 [ 3 ]                │
├───────────────────────────┬──────────────────────────────┤
│ 我方（全部已知）           │ 对方（只知道种类）            │
│ 精灵 [水灵 ▾]              │ 精灵 [龙息帕尔 ▾]             │
│ 性格 [聪明 ▾]              │ 魔防 145～217（150 种可能）   │
│ 天分 [魔攻 10 ▾]           │ 生命 362～510                │
│ 六维：精确数字             │ 可能性格：30 种（可展开）      │
│ 增减益：物攻/物防/魔攻/     │ 增减益：物攻/物防/魔攻/       │
│ 魔防/速度，各一排加减按钮   │ 魔防/速度，各一排加减按钮      │
├───────────────────────────┴──────────────────────────────┤
│ 技能 [搜索框 / 下拉列表]                                  │
│ 伤害范围：140 ～ 210                                      │
│   防御最低 145 → 210；防御最高 217 → 140                  │
│ 占对方生命：约 27% ～ 58%（对方生命越低占比越高）          │
│ 能否击倒：不能（对方生命至少 362）                        │
├──────────────────────────────────────────────────────────┤
│ 战斗记录                        [＋ 记录伤害] [＋ 记录生命%]│
│ ① 我方 水灵 用 气泡 打对方 341（雨天，我方魔攻 +2）        │
│    → 对方魔防锁定 156；可能性格 20 种                      │
│ ② 打完这一下后，对方剩余生命 50%（累计伤害 195）           │
│    → 对方最大生命锁定 391；可能性格再缩小                  │
│ ③ ...                                                     │
└──────────────────────────────────────────────────────────┘
```

交互要点：

- 对方的数值用“最低～最高”显示；只剩下一个值时显示单个数。
- 鼠标悬停或展开，可以看到“可能的数值列表”和“可能性格列表”。
- 每条战斗记录可以编辑、删除；改动后所有范围立即重算。
- 页面状态自动保存在浏览器本地（localStorage），刷新不丢；以后再加导出/导入 JSON。

## 4. 对方未知信息怎么算成范围

### 4.1 未知的是什么

- 对方是哪个精灵、什么属性：看得到，已知。
- 对方性格：30 种，每种提升一项属性、降低另一项属性，没有“不加不减”的性格。
- 对方天分：每项只能是 **0、7、8、9、10**（用户确认，不存在 1～6），至多三项有加成。

### 4.2 单项属性的候选值

对单独一项属性来说，可能值是「30 种性格 × 5 种天分 = **150 种组合**」。因为把其他天分都设为 0 时，单项天分仍可取任意合法值，所以“最多三项”的限制不影响单项范围。

150 种组合里很多数值相同。因为天分有 5 档、性格对该项只有“提升 / 降低 / 不影响”3 种，单项最多只有 **15 个不同数值**。

以 60 级的龙息帕尔为例，初始范围是：

| 属性 | 最低～最高 | 不同数值个数 |
|------|------------|--------------|
| 生命 | 362～510 | 15 |
| 物攻 | 185～270 | 15 |
| 物防 | 189～274 | 15 |
| 魔攻 | 116～177 | 15 |
| 魔防 | 145～217 | 15 |
| 速度 | 158～234 | 15 |

这些数字全部由现有的 `calculate_stat()` 逐个组合算出，不另写公式。

### 4.3 从属性范围到伤害范围

伤害公式里，防御在分母，所以：

- 防御越高，伤害越低；防御越低，伤害越高。
- 攻击越高，伤害越高。

因此只需要取候选值的最小值和最大值，就能得到伤害范围：

```text
最大伤害 = 用最低防御算出的伤害
最小伤害 = 用最高防御算出的伤害
```

例：水灵（聪明、魔攻天分 10，魔攻 270）用气泡打未知的龙息帕尔：

```text
魔防候选 145～217
防御 145 → 伤害 210
防御 217 → 伤害 140
所以伤害范围是 140～210
```

### 4.4 战斗记录怎么缩小范围

一条记录包含：哪一方攻击、用的什么技能、打了多少血、打了几下、当时的天气 / 增减益 / 星陨层数。

处理方式：

1. 取受击方对应防御属性的 150 个候选值（物攻技能看物防，魔攻技能看魔防）。
2. 对每个候选值，用与网页相同的伤害公式模拟一次。
3. 只保留模拟结果正好等于记录伤害的候选值。
4. 剩下的候选值决定新的范围、剩余组合数和可能性格。

例：记录“雨天，水灵用气泡打了龙息帕尔 341”：

```text
150 个魔防候选里，只有 156 能打出 341
剩下 20 种组合，对应 20 种性格
这 20 种性格都不提升也不降低魔防，且魔防天分为 0
```

也就是说，这一条记录已经确认了对方的魔防天分为 0，并排除了 10 种会改变魔防的性格。

如果一条记录没有任何候选值能对上：

- 不缩小范围，保留记录并标红提示。
- 提示内容：“这条记录和当前规则对不上，请检查伤害、天气、增减益或星陨层数。”
- 常见原因：对方有减伤特性/道具、记录的是多段技能的单段伤害、天气或增减益填错。

### 4.5 多条记录

- 同一条属性上的多条记录，依次过滤同一组候选值。
- 不同属性上的记录（例如物防和魔防各一条），分别过滤；展示“可能性格”时取各属性的交集。
- 第一版按填写顺序处理；某条记录把候选值过滤到 0 时，标红并跳过这一条，不让整个结果变空。

### 4.6 生命百分比记录

对方不会显示具体生命，只显示“剩余生命 ÷ 最大生命”的整数百分比，默认四舍五入。记录一条生命百分比需要两个数：

- 当时显示的百分比，例如 `50`。
- 到那一刻为止，对方累计受到多少伤害。默认由之前记在同一只对方精灵身上的伤害自动累加，也可以手动修改（中途开始记录、对方回血、漏记伤害时用）。

处理方式和伤害记录一样，逐个试 150 个生命候选值：

```text
显示百分比 = round((最大生命 − 累计伤害) ÷ 最大生命 × 100)
只保留算出来等于记录值的候选
```

例：无雨时水灵气泡打龙息帕尔是 195 伤害，打完后对方显示还剩 **50%**：

```text
391 → (391−195)/391 = 50.13% → 显示 50
394 → (394−195)/394 = 50.51% → 显示 51
其他生命候选也都不是 50
→ 最大生命锁定 391
→ 生命天分是 0，性格不改变生命
→ 可能性格从 30 种缩小到 20 种
```

如果同时还记录了别的属性（例如魔防锁定 156），展示“可能性格”时会把各属性剩下的性格取交集。

边界情况：

- **百分比取整方向**：先按四舍五入。接口里留一个 `round` / `floor` / `ceil` 选项；如果记录怎么都对不上，可以换一种取整方式再试。
- **0%**：表示剩余生命不足 1%，可能已经倒下。只用来给最大生命一个上界，不强行推断具体数值。
- **治疗**：回血后“累计伤害”不再等于已损失生命，需要手动改小这个数字。
- **护盾**：护盾吸收的伤害不算生命损失，百分比可能对不上；这时会提示而不会硬算。
- **过量伤害**：累计伤害可以大于最大生命，这种情况只保留“已经击倒”的判断。

### 4.7 生命占比和能否击倒

对方生命也是未知的。第一版用“最乐观 / 最悲观”两组数字给出一个略宽的范围：

```text
最小占比 = 最小伤害 / 最大生命
最大占比 = 最大伤害 / 最小生命

一定击倒：最小伤害 ≥ 最大生命
不能击倒：最大伤害 < 最小生命
其余情况：可能击倒
```

例：气泡伤害锁定 341、对方生命范围 362～510 时，341 < 362，所以“不能击倒”。

### 4.8 已知的近似

- 每项属性分开推断，没有校验“最多三项天分”在多项属性之间的组合限制。例如四条记录分别要求四项天分都非 0 时，真实游戏里不可能，但第一版仍会保留。后续可以加联合校验。
- 生命占比和能否击倒用的是独立的最乐观/最悲观值，比真实可能性略宽。
- 对方可能有减伤特性、道具、护盾，这些目前都不知道；记录对不上时会提示，而不是强行套公式。
- 生命百分比依赖“累计伤害”记录完整。治疗、护盾、漏记伤害不会自动识别，需要手动调整累计伤害。
- 生命百分比默认按四舍五入处理；如果游戏实际是向下或向上取整，需要切换选项。

## 5. 接口设计

### 5.1 Python 函数层

新增 `roco_analysis.py`，核心函数：

```python
def analyze_battle(state: dict) -> dict:
    """输入整场状态，返回对方属性范围和当前技能伤害范围。"""

def stat_candidates(pet, stat_key, level=60) -> list:
    """返回 150 个候选：{value, nature, talent}。"""

def apply_observation(candidates, observation, ...) -> list:
    """用一条战斗记录过滤候选值。"""
```

网页服务只是这些函数的薄包装，以后其他程序也可以直接 `import roco_analysis` 调用。

### 5.2 网页接口

| 方法 | 路径 | 作用 |
|------|------|------|
| GET | `/api/meta` | 一次返回精灵、性格、攻击技能列表 |
| POST | `/api/analyze` | 输入整场状态，返回范围结果 |

`GET /api/meta` 返回：

```json
{
  "pets": [{"number": "295", "name": "龙息帕尔", "form": "", "types": ["恶系"]}],
  "natures": [{"name": "聪明", "up_name": "魔攻", "down_name": "物攻"}],
  "skills": [{"name": "气泡", "element": "水系", "damage_class": "魔攻", "power": 100, "energy": 3}]
}
```

`POST /api/analyze` 请求：

```json
{
  "our_pet": {
    "name": "水灵",
    "form": null,
    "nature": "聪明",
    "talents": {"spa": 10},
    "buffs": {"spa": 2}
  },
  "opponent_pet": {
    "name": "龙息帕尔",
    "form": null,
    "buffs": {}
  },
  "weather": "雨天",
  "starfall_layers": 0,
  "skill": "气泡",
  "hp_percent_rounding": "round",
  "observations": [
    {
      "type": "damage",
      "attacker": "our",
      "skill": "气泡",
      "damage": 341,
      "hits": 1,
      "weather": "雨天",
      "our_buffs": {"spa": 2},
      "their_buffs": {},
      "starfall_layers": 0,
      "damage_reduction_percent": 0,
      "damage_multiplier_percent": 100
    }
  ]
}
```

响应：

```json
{
  "opponent": {
    "pet": "龙息帕尔",
    "level": 60,
    "stats": {
      "hp":  {"min": 362, "max": 510, "possible_values": [362, 391, 394], "remaining": 150, "total": 150},
      "atk": {"min": 185, "max": 270, "possible_values": [185, 200, 206], "remaining": 150, "total": 150},
      "def": {"min": 189, "max": 274, "possible_values": [189, 204, 209], "remaining": 150, "total": 150},
      "spa": {"min": 116, "max": 177, "possible_values": [116, 123, 136], "remaining": 150, "total": 150},
      "spd": {"min": 156, "max": 156, "possible_values": [156], "remaining": 20, "total": 150},
      "spe": {"min": 158, "max": 234, "possible_values": [158, 170, 179], "remaining": 150, "total": 150}
    },
    "possible_natures": ["大胆", "固执", "勇敢", "逞强", "稳重", "..."],
    "observations": [
      {"index": 0, "type": "damage", "matched": true, "kept": 20, "message": null}
    ],
    "warnings": []
  },
  "damage": {
    "skill": "气泡",
    "min": 341,
    "max": 341,
    "min_case_defense": 156,
    "max_case_defense": 156,
    "damage_percent_min": 66.9,
    "damage_percent_max": 94.2,
    "knockout": "impossible"
  }
}
```

说明：

- `possible_values` 最多 15 个，直接给前端做“可能的数值”展示；上面的示例为了节省篇幅，每项只列了前 3 个。
- `remaining` 是剩下的（性格, 天分）组合数；`total` 固定 150。
- `knockout` 取值：`certain`（一定击倒）、`possible`（可能击倒）、`impossible`（不能击倒）。
- 出错时返回 HTTP 400 和 `{"error": "中文原因"}`，不返回堆栈。

**生命百分比记录示例**

另一场：无雨时水灵气泡造成 195 伤害，打完后对方显示还剩 50%。在 `observations` 里加一条：

```json
{
  "type": "hp_percent",
  "hp_percent": 50,
  "total_damage": 195
}
```

对应响应里的生命会变成：

```json
"hp": {"min": 391, "max": 391, "possible_values": [391], "remaining": 20, "total": 150},
"observations": [
  {"index": 0, "type": "hp_percent", "matched": true, "kept": 20, "message": null}
]
```

说明：

- `total_damage` 是“到那一刻为止，对方累计受到的伤害”。前端默认用之前的伤害记录自动累加，用户可以手动修改。
- `type` 省略时默认按 `damage` 处理，方便只记伤害的旧请求继续使用。
- `hp_percent_rounding` 支持 `round`（四舍五入，默认）、`floor`（向下）、`ceil`（向上）。
- 生命百分比和伤害记录可以混在同一个数组里，按填写顺序逐条应用。

### 5.3 增减益接口

请求里每方一个 `buffs` 对象：

```json
{"atk": 0, "def": 0, "spa": 2, "spd": 0, "spe": 0}
```

- 物攻/物防/魔攻/魔防每层 10 个百分点；速度每层 +10 点。
- 范围 −99～99 层，和命令行一致。
- 每条战斗记录单独保存当时的增减益，不用现在的状态解释以前的伤害。
- 页面“高级”区保留手填 `damage_reduction_percent`、`damage_multiplier_percent`、`hits` 的入口，对应命令行已有的参数。

## 7. 决策记录

- 前端不引入 Node、不安装新软件，用 Python 自带服务器 + 普通网页。
- 对方每项属性独立推断；单项候选 = 30 种性格 × 5 种天分 = 150 种组合。
- 天分只允许 0、7、8、9、10（2026-11-21 用户确认）。
- 伤害范围只取防御候选的最低/最高值，因为伤害随防御单调变化。
- 战斗记录采用“候选值逐个模拟、保留能对上的”方式，不用反推公式。
- 记录对不上时不缩小范围，只警告，不静默改数。
- 服务状态放在前端；后端接口无状态，每次请求带完整状态，方便以后接别的程序。
- 第一版只做“我方打对方”；对方打我方在接口里预留 `attacker` / `defender` 字段。
- 对方生命只显示整数百分比，默认四舍五入（2026-11-21 用户确认）；接口保留 `round` / `floor` / `ceil` 切换。
- 生命百分比记录使用“当时累计伤害”而不是“这一下打了多少”，由前端自动累加、允许手动修改；治疗和护盾需要手动调整。
